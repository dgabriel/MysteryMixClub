# Agent-workflow observability (MysteryMixClub-ysu2)

Meta-tooling that measures what **this repo's own Claude Code multi-agent
workflow** (developer / tester / reviewer / ui-agent / product-manager /
uiux-designer / devops subagents) costs in tokens and dollars.

**This is not MysteryMixClub's own application observability.** That's a
separate, already-filed concern (`MysteryMixClub-p0qzz0`, "Build observability
for fast debug") with its own infra. Nothing here touches `backend/`, the
app's `docker-compose.yml`, or app runtime metrics -- this stack is entirely
self-contained under `observability/`.

## What's here

```
observability/
  docker-compose.yml               Prometheus + Grafana, local-only, no cloud dependency
  prometheus/prometheus.yml        Scrape config (60s interval, localhost:9464/metrics)
  grafana/
    provisioning/                  Datasource + dashboard provider, as code
    dashboards/claude-code-agent-usage.json   The dashboard itself, as code
  backfill/
    extract_usage.py               ONE-TIME script: reconstructs historical usage
                                    from ~/.claude/projects/*/*.jsonl
    load_backfill.sh               Loads the extracted data into Prometheus's TSDB
    output/                        Generated by the above (gitignored)
  smoketest/
    fake_claude_metrics.py         Dev-only fixture: fakes the /metrics endpoint
                                    shape so you can verify the stack before
                                    real telemetry is on. Not part of the pipeline.
```

## The one thing you still need to do (I did not do this)

Per the ticket's own explicit scope boundary, I did **not** touch your shell
profile. Add these two lines yourself (e.g. `~/.zshrc`), wherever you keep
other exported env vars, then open a new terminal / `source` it:

```sh
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=prometheus
```

That's it -- no endpoint URL needed for the `prometheus` exporter; Claude Code
serves `/metrics` on `localhost:9464` by default whenever a Claude Code
session is running with these set. The scrape interval Prometheus uses here
(60s) matches Claude Code's own default `OTEL_METRIC_EXPORT_INTERVAL`
(60000ms), so you don't need to touch that either unless you want tighter
resolution.

This is a global, cross-project environment change (it affects every Claude
Code session on this machine, not just MMC), which is exactly why it's your
call and not mine.

## Starting the stack

```sh
cd observability
docker-compose up -d
```

- Prometheus: http://localhost:9090 (scrape target status: http://localhost:9090/targets)
- Grafana: http://localhost:3001 (anonymous viewer access is enabled; no login needed to just look at the dashboard)
- Dashboard: **Claude Code Agent Workflow** folder -> "Claude Code Agent Workflow - Token & Cost Usage (MysteryMixClub-ysu2)"

Both are pinned images (`prom/prometheus:v3.13.1`, `grafana/grafana:11.4.0`)
with named Docker volumes (`observability_prometheus-data`,
`observability_grafana-data`) for persistence across restarts. `docker-compose
down` alone preserves the data; `docker-compose down -v` wipes it.

### Verifying the pipe before you set the real env vars

You don't have to wait for real telemetry to confirm the stack itself works.
`smoketest/fake_claude_metrics.py` serves a synthetic `/metrics` endpoint on
`:9464` shaped like Claude Code's real exporter output:

```sh
python3 observability/smoketest/fake_claude_metrics.py &
cd observability && docker-compose up -d
# then check http://localhost:9090/targets -- claude-code-agent-workflow should be "up"
```

I ran exactly this before writing this doc (see report / PR description for
what I verified). Stop it with `pkill -f fake_claude_metrics.py` once you've
confirmed the pipe and before you start using the real thing on the same port.

## The dashboard

One provisioned dashboard, panels grouped into three rows:

1. **Pipe health** -- `claude_code.session.count` by source (the acceptance
   criterion: confirms live data is flowing at all), scrape target `up`, and a
   sanity count of distinct `source` values loaded (expect 2 once both live
   and backfill have run: `live`, `backfill`).
2. **Core metric** -- tokens-per-PR (overall), token usage by `agent.name`,
   token usage by `type` (cache breakdown), and a dedicated cache-hit-ratio
   panel (`cacheRead / (cacheRead + cacheCreation + input)`) -- called out in
   the ticket as the single most important cost lever.
3. **Secondary** -- cost usage (USD) by model + `agent.name`, commit count,
   lines of code by type/model, active time by type (user/cli).

A `source` dashboard variable lets you view `live`, `backfill`, or both
together on every panel.

### Known limitation: `agent.name` on *live* data will mostly say "custom"

I read Claude Code's OTel docs (`https://code.claude.com/docs/en/monitoring-usage`)
in full before building this, specifically to confirm `agent.name` behavior.
Relevant quote:

> `agent.name`: Subagent type that issued the request. Built-in agent names
> and agents from official-marketplace plugins appear verbatim. **Other
> user-defined agent names are replaced with `"custom"`.** Absent when the
> request was not issued by a named subagent type.

MMC's five subagents (`.claude/agents/{developer,tester,reviewer,ui-agent,
uiux-designer,devops}.md`) are project-local, user-defined agents -- not
built-in and not installed from an official marketplace plugin. **That means
live telemetry going forward will report all of them collapsed under
`agent_name="custom"`**, not individually. The main session (no subagent) has
no `agent.name` at all. This directly limits the ticket's stated goal of
seeing "cost distributed across developer/tester/reviewer/ui-agent/
product-manager" from **live** data.

The **backfill** data does not have this problem -- I derive `agent_name` from
each subagent invocation's own transcript metadata
(`.meta.json`'s `customAgentType`/`agentType`), so it's fully granular
(`developer`, `tester`, `reviewer`, `ui-agent`, `uiux-designer`, `devops`,
`main`, plus Claude Code's built-in `explore`/`plan`/`general-purpose`
buckets for ad hoc Task-tool calls, and `other` for anything unrecognized).

I did not attempt to work around the live-side limitation (e.g. publishing
MMC's agents as a marketplace plugin) -- that's a real product/workflow
change, not a monitoring change, and belongs in its own ticket. See
"Candidate follow-up tickets" below.

### Why panel queries use `{__name__=~"claude_code_token_usage.*"}` instead of a fixed metric name

Claude Code's OTel-to-Prometheus metric naming (dot-to-underscore, `_total`
suffixing for counters, unit-suffix omission when `prometheus` is the only
exporter) is documented at the semantic level but I could not get a live
`/metrics` sample from a real Claude Code process to confirm the exact
resulting name byte-for-byte (that requires the env vars only you can set).
Rather than hardcode a guess, every panel matches on a `__name__` regex
prefix, which is robust to whatever exact suffix the real exporter uses. If
the very first thing you check (`claude_code.session.count` pipe-health
panel) shows no live data once the env vars are set and a session is
running, that's the first thing to check: `curl localhost:9464/metrics` on
the host and compare the literal metric names against the dashboard's regex.

### Why `claude_code.pull_request.count` isn't sliced by `agent.name` in the "tokens per PR" panel

Per the same docs, `claude_code.pull_request.count`'s only attributes are the
standard ones -- no `agent.name`. So the ticket's core-metric formula (`sum(
token.usage) / sum(pull_request.count)`, "sliced by agent.name") can't
literally be computed as a single per-agent ratio from live OTel data; PRs
aren't attributed to an agent upstream. I implemented this as two adjacent
panels instead: the overall tokens-per-PR ratio, and a separate per-agent
token breakdown, which together cover the same analytical ground the ticket
is after. Flagging this as a deliberate interpretation, not a silent
deviation.

## Running the backfill (manual one-off, not a scheduled job)

```sh
cd observability/backfill
python3 extract_usage.py            # writes output/usage_events_raw.jsonl + output/claude_code_backfill.om
./load_backfill.sh                  # requires the stack to already be up
```

`extract_usage.py --dry-run` prints summary stats (files scanned, distinct
sessions/PRs, date range, total tokens, any unpriced models) without writing
anything -- useful to sanity-check before loading.

What it does, in short (full detail in the script's own docstring):

- Walks `~/.claude/projects/<mangled-repo-path>/` -- both the top-level
  session transcripts (the "main" orchestrator) and `*/subagents/*.jsonl`
  (individual subagent invocations, matched to their `.meta.json` for agent
  identity).
- Dedupes by Anthropic message id (a single API response is split across
  multiple transcript lines, one per content block -- thinking/tool_use/text
  -- all sharing one usage blob; naively summing every line would multiply
  token counts by the number of content blocks per response).
- Buckets into **daily** counters (not per-request) and writes them as
  cumulative OpenMetrics samples, every series tagged `source="backfill"` --
  never `source="live"` -- so the two are always distinguishable in every
  query and panel.
- By default, only backfills **up through yesterday (UTC)**, not today. This
  is deliberate, not just a "pre-instrumentation period" framing choice:
  Prometheus's TSDB head rejects any newly-scraped (live) sample that is
  chronologically older than a block already ingested. If the backfill
  included today and a live scrape from earlier today came in after, it would
  get rejected as "too old" until wall-clock time caught up. Pass
  `--before <ISO8601 timestamp>` (e.g. the exact moment you set
  `CLAUDE_CODE_ENABLE_TELEMETRY=1`) to top up a narrower window later without
  ever overlapping live data.
- Cost is a best-effort estimate from a small hardcoded per-model-family price
  table in the script (`opus`/`sonnet`/`haiku` substring match; cache write
  assumed at 1.25x input price, cache read at 0.1x -- Anthropic's standard
  cache pricing ratios). It will go stale. Per the ticket's own note and
  Claude Code's docs: **treat `/cost` and provider billing as ground truth**;
  this is for relative agent/model comparison only. Models it doesn't
  recognize (e.g. internal/experimental model names) are reported but left
  unpriced, with a warning, rather than guessed at.

`load_backfill.sh` then: validates the OpenMetrics file with `promtool check
metrics`, converts it to TSDB blocks with `promtool tsdb
create-blocks-from openmetrics`, `docker cp`s each block into the running
Prometheus container, **`chown`s them to `nobody:nobody`** (the image's
runtime user -- `docker cp` preserves host ownership, and without this step
Prometheus can read the blocks fine but fails to ever compact/delete them,
which silently wedges the database over time), and restarts Prometheus to
pick them up.

### If you ever need to re-run this

- Safe to re-run against a fresh `.om` file at any time; Prometheus does not
  deduplicate blocks on overlapping data, so prefer a `--before` cutoff on
  re-runs to avoid double-counting a window you've already loaded.
- If Claude Code changes its transcript format in a future release and this
  script starts erroring or silently under-counting, that's expected per the
  ticket ("internal format ... changes between releases") -- fix the parser
  at that point, don't try to keep it running unattended in the meantime.

## Validated before hand-off

I brought the real stack up locally and confirmed, before writing this
report:

- `docker-compose up -d` succeeds; both containers reach a healthy state.
- Grafana provisioning loads the datasource (correct `uid`, points at
  `http://prometheus:9090`) and the dashboard (correct folder, 15 panels)
  automatically -- nothing clicked together by hand.
- Using the `smoketest/fake_claude_metrics.py` fixture standing in for a real
  Claude Code process: Prometheus's scrape target goes `up`, and every panel
  query in the dashboard (session count, per-agent token breakdown, cache hit
  ratio, tokens-per-PR) returns real, sensible values against it.
- Ran `extract_usage.py` for real against this machine's actual MMC
  transcripts (35 main sessions, 132 subagent invocations, ~15k deduped API
  requests, 2026-06-26 through 2026-07-25) and `load_backfill.sh` against the
  live stack: backfilled data loads, is queryable at its real historical
  timestamps, is correctly broken down by `agent_name` into
  `developer`/`tester`/`reviewer`/`devops`/`main`, and coexists with ongoing
  live scraping without interference (`source="live"` kept accumulating
  normally throughout).
- Found and fixed two real bugs in this process before calling it done: (1)
  end-of-day bucket timestamps could land in the future relative to
  wall-clock and starve live ingestion -- fixed by bucketing at start-of-day
  and excluding "today" by default; (2) `docker cp`'d blocks are owned by the
  host user, not the container's `nobody` user, which silently breaks
  Prometheus's later compaction -- fixed with an explicit `chown` step in
  `load_backfill.sh`.
- Tore the test stack down (`docker-compose down -v`) and cleared the test
  backfill output afterward, so what's committed is clean instrumentation,
  not leftover test state.
